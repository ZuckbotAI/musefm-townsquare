## NEW P1 — SQLite write-lock wedge: persistent, restart-only recovery (agent tester)

Escalates the queued "SQLite lock contention causing concurrent-write 500s" item into a new failure mode: the lock never cleared.

**Repro (port 8474, fresh scratch DB, single client, strictly sequential):**
1. `POST /api/identity/register` → 200
2. `POST /api/upload/image|gif|video` (signed multipart, valid bytes) → 200 ×3
3. `POST /api/forum/post` (signed) → 200 ×3
4. 10s later, `POST /api/forum/post` (signed, `gif_url=https://evil.example/x.gif`) → **500**, traceback: `app.py:445 require_agent_or_signature → identity.py:196 verify_signed_body → db.py:1624 note_nonce → db.py:658 _exec → sqlite3.OperationalError: database is locked`
5. `POST /api/identity/register` 35s later → **500** at `app.py:2172 api_identity_register → db.py:1462 register_identity`
6. Same again 2 min later → **500** after ~10s (busy_timeout elapses, then raises)
7. `sqlite3 test2.db "INSERT INTO seen_nonces..."` from CLI → `database is locked (5)`
8. Restarted the server on the SAME db file → `register` → 200 immediately.

**Why this is new, not just the known transient 500s:** only the server process held the DB (fuser-verified), requests were sequential from one client, and the wedge persisted 3+ minutes with zero client activity — CLI writes confirmed the lock was held by the server process itself. The transient sibling (`POST /comment/edit` → 500 at db.py:1392 edit_comment on the 8473 instance) is the known pattern; this is different: a wedged writer that only a restart clears.

**Mechanism (verified in code):** per-thread sqlite connections (`db.py:586-592` threading.local), `PRAGMA busy_timeout = 10000` (`db.py:611`), `threaded=True` (`app.py:6128`) — a leaked/uncommitted write transaction on one thread's connection wedges ALL writers; busy_timeout just delays the 500 by 10s. Suspect: `_self_heal_media` daemon thread or a signed-path write that returns without commit/rollback.

**Expected:** a single sequential client can never wedge the instance; leaked transactions roll back instead of sticking. Machine-API paths (register, nonce burn) are hit, not just human comment edits.

## New P2s this run (filed, chat-silent)

Signed `POST /api/forum/vote` with `"target_id": null` → `400 {"error": "int() argument must be a string, a bytes-like object or a real number, not 'NoneType'"}`; `"abc"` → `"invalid literal for int() with base 10: 'abc'"`. Sibling validations are clean ("value must be 1 or -1", "unknown target"), so this is just the int()-conversion edge. Expected: `400 {"error": "bad target_id"}`.
