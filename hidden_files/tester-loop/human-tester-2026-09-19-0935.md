## Bugs found

### P1 — none new. P0 — none.

### P2 (nits / polish)
1. **Votes and reactions on nonexistent targets fail silently.** POST /vote with target_id=99999/0/-5 or value="banana", and /fb_react with an invalid reaction name, all return 302 with zero feedback. Nothing breaks and nothing bad is stored, but a human clicking a broken/react-picker edge gets no signal anything happened. Repro: any of the curl/python snippets above against /vote or /fb_react. Expected: a 400 or an error flash for malformed input.
2. **Long comments truncated without feedback.** 10,000-char body → stored as 2000 chars, no notice. Repro: POST /post/8/comment with 10k body (this run: comment id 8, LENGTH(body)=2000). Expected: either reject >2000 with a message or tell the user it was trimmed.
3. **/submit has no CSRF token.** The post-composer form carries no synchronizer token (unlike /vote, /fb_react, comments, which all require `csrf_token`). It relies on session-cookie auth alone. Low practical risk for this app, but inconsistent with the rest of the surface — the file header comment even says "POST-only for every state-changing human web form". Repro: POST /submit with no csrf_token field → 302 success (this run: posts.id 8, 9 via plain multipart). Severity P2 (session-riding exposure on the highest-value write endpoint).

### Known-issue dedupe (not new)
- **SQLite "database is locked" → 500** observed once on POST /fb_react at 2026-09-19 14:39:24 UTC (server.log line ~285: `sqlite3.OperationalError: database is locked` in db.py `_exec`). Triggered by three test subagents writing concurrently against the single-threaded dev server. This matches the existing defect-queue entry ("SQLite lock contention causing concurrent-write 500s", 2026-09-18) — **not re-reported as new**.

### Testing artifact (NOT an app bug)
- `curl -F "body=<b>bold</b>"` consistently returned HTTP:000 (curl exit 26) while the identical payload via python-requests multipart and via urlencoded curl worked fine (302/429). Root cause: curl's `-F` interprets a leading `<` as file-read syntax. Do not treat as a server-side HTML-filter bug; requests with `<script>` payloads reached the app normally and were escaped correctly.
