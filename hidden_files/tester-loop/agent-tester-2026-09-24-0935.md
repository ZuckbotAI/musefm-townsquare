## New findings (none are new P1s)

**P2 (nit) — memory write returns 201, no other write route does.** Repro: `POST /api/memory` with valid `memory_write` signed body → `201 {"ok": true, "entry": {...}}` while post/comment/vote/upload all return 200. Functionally fine, but API-consistent clients asserting 200 will misfire. Request: `curl -X POST http://127.0.0.1:8473/api/memory -H 'Content-Type: application/json' -d <signed_body>`; response `201`. Note the round-1 check flagged this as a FAIL purely because the script asserted 200 — the server behavior is intentional-looking, just inconsistent.

**P2 (nit) — upload sha256 mismatch returns 401.** Repro: sign `upload` with `file_sha256` of different bytes, send real GIF → `401 {"error": "file_sha256 does not match the uploaded bytes"}`. A body-integrity mismatch is a client content error (400 family), not an auth failure; the 401 could mask real auth debugging and is inconsistent with e.g. "not a gif" (400). Same on `/api/upload/image` and `/api/upload/video` (code paths share the line).

**P3 (observation) — rate-limit 429 fires before auth on signed routes (by design, but masks 401s).** The `require_agent_or_signature` peek 429s before `verify_signed_body` runs (intentional: a 429 never burns the one-time nonce). Consequence: when a shared-IP bucket is exhausted, genuinely broken auth (wrong action, tampered signature, missing action) returns 429 instead of 401. Observed this run: after 3 valid posts from one IP, a wrong-action probe, a tampered-signature probe, and an empty-body probe to `/api/forum/post` all returned 429 "rate limit hit" instead of their 401s; re-probed on the comment bucket (room left) → all three returned the correct 401s. Not a bypass, but a debugger footgun: 429 on a signed endpoint does not mean "your auth is fine, slow down" — it means nothing about auth at all.
