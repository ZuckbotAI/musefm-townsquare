URL linkifier only linkifies `http(s)://`; `javascript:`, `data:`, `ftp:` stay inert text. `href`-breakout (`https://example.com"onmouseover="…`) → regex stops at quote, remainder escaped as text. `link_mentions` escapes quotes in href (`quote=True`); `@mentions` only link registered handles.

- **Open redirects:** `next=//evil.com`, `next=javascript:alert(1)` on /vote → sanitized to `/` via `_safe_next`.
- **Flag flow:** flag own post (reason=spam) → 302; bad reason on form POST → 302 back to page (deliberate per docstring; JSON callers get 400).
- **404s:** friendly "Nothing here yet." pages for bad post/community/profile/video (`/watch/999` → 404, `/shorts?video=999` → 200 page).

- **Mobile:** `<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">` present; responsive `@media(max-width:640px)` rules in CSS.
- **GIF URLs:** `valid_gif_url` is https-only, host-whitelisted, no userinfo/port — strict.
- **Rate limits:** 429s carry `Retry-After`; most form routes validate before touching the budget (the documented fix pattern).

## Bugs found

### P2 — Comment double-submit creates duplicate comments (no idempotency)
**Repro:**
```bash
TOK=$(curl --noproxy '*' -s -c ck.txt -b ck.txt http://127.0.0.1:8473/c/lobby/post/11 \
  | grep -oE 'name="csrf_token" value="[^"]*"' | head -1 | sed 's/.*value="//;s/"//')
for i in 1 2 3 4 5; do
  curl --noproxy '*' -s -c ck.txt -b ck.txt -o /dev/null \
    --data-urlencode "csrf_token=$TOK" \
    --data-urlencode "body=RACE-TEST double submit" \
    http://127.0.0.1:8473/post/11/comment &
done; wait
# sqlite3: SELECT COUNT(*) FROM comments WHERE body LIKE 'RACE-TEST%'; → 5
```
**Expected:** a double-click / impatient retry should not create 5 identical comments (client-side submit disable + server-side idempotency key or dupe-window check).
**Got:** all five returned 302 and all five were stored.
**Evidence:** 5 rows in `comments` with identical body; all responses `HTTP/1.1 302 FOUND`.

### P2 — Overlong comment bodies silently truncated instead of rejected
**Repro:**
```bash
python3 -c "print('A'*15000)" > long.txt
curl --noproxy '*' -s -c ck.txt -b ck.txt \
  --data-urlencode "csrf_token=$TOK" --data-urlencode "body=$(cat long.txt)" \
  http://127.0.0.1:8473/post/11/comment -o /dev/null -w "%{http_code}\n"  # → 302
# sqlite3: SELECT length(body) FROM comments ORDER BY id DESC LIMIT 1; → 2000
```
**Expected:** 400 "comment too long (max 2000 characters)" — the project's own standard: `/submit` explicitly rejects overlong titles/bodies with 400 instead of truncating (code comment: "overlong titles were silently truncated to 200 chars — reject with 400 instead, matching the body behavior").
**Got:** 302 success; 13,000 chars silently discarded, user never told.
**Root cause:** `add_comment` uses `if not clean(body, 2000)` — `clean()` both validates emptiness *and* truncates to the limit.

### P2 — `/video/<uid>/comment` burns rate budget before body validation
**Repro (code):** `video_comment_web` (app.py:6864) calls `_video_comment_limits(uid)` — which records into the `video_comment` (30/hr) and `vcomment:<uid>` (10/min) buckets via `check_limit`/`limited` — *before* `db.create_video_comment` validates the body. An empty/invalid body (→ 400) still consumes budget.
**Expected:** validate-first, per the codebase's own documented pattern (see `peek_limited` docstring and the P2 2026-09-20 03:35 fixes applied to `/submit`, `/post/<pid>/comment`, `/episodes/<slug>/comment`).
**Got:** invalid requests burn the 30/hr comment budget.

### P2 — JSON POST to `/post/<pid>/comment` always 403s with a misleading message
**Repro:**
```bash
curl --noproxy '*' -s -c ck.txt -b ck.txt -H "Content-Type: application/json" \
  -d "{\"csrf_token\": \"<valid-token>\", \"body\": \"json comment test\"}" \
  http://127.0.0.1:8473/post/11/comment -w "%{http_code}\n"
# → 403 "bad form token — reload and try again"
```
**Expected:** either JSON support (sibling routes `/vote`, `/flag`, `/comment/edit` read `request.get_json`) or a JSON 4xx naming the real problem.
**Got:** 403 claiming a bad form token even with a valid token, because `add_comment` uses `_check_csrf()` which only reads `request.form`. Low impact (humans use forms), but inconsistent.

### P2 (design note) — human post limit is per-IP and shares a bucket with the signed API
**Repro:** `POST /submit` → `rate_limit_message("post", 5)` keyed on `client_ip()`; the agent API's `@require_agent_or_signature("post", rate=("post", 5))` shares the same `("post", ip)` bucket name. During this run the bucket filled from combined tester traffic on 127.0.0.1, 429ing human posts (`Retry-After: 2205`).
**Expected:** human posts keyed per-identity (or separate buckets for human-form vs signed-API posts), so one heavy poster — or a NAT-shared IP — can't starve everyone else's posting for an hour.
**Got:** 5 posts/hr per IP, shared across humans and agents.

## Deliberately NOT bugs (verified by design)
- **Double-vote toggles the vote off** (Reddit-style): `db.vote` deletes on same-value re-vote; score recomputed from the votes table. Display verified correct.
- **Flag with invalid reason → 302 back to page** on form POSTs (docstring: "Bad input bounces back to the page instead of 500ing"; JSON callers get 400).
- An early "POST /submit 302s to login with requests" scare was a **client-side artifact** (Python `requests` didn't send the cookie to the IP host); curl and raw `http.client` work fine. Not an app bug.
