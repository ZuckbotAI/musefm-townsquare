## New bugs

### P2-1. Session cookie missing `Secure` flag
`app.py:326` sets `SESSION_COOKIE_SAMESITE="Lax"`; `HttpOnly` is Flask's default
True. `SESSION_COOKIE_SECURE` is never set. On the production HTTPS origin the
session cookie is emitted without `Secure`. Low severity (production is
HTTPS-only via Render) but it's a one-line hardening fix. Not in any prior
48h report.

### P2-2. Import-time `init_db` writes to the DEFAULT database even when `--db` is given
`app.py:256` runs `db = init_db(DB_PATH)` **at import**, and `init_db` executes
every schema ensure + seeds + `_run_startup_media_cleanup` against the default
path (`./townsquare.db`, or `TOWNSQUARE_DB` env) *before* `__main__` rebinds to
`--db`. Consequences observed this run (see Incident below): any
`python3 app.py --db <scratch>` boot **and any pytest process that imports
`app`** touches the checkout's real DB file. `--db` isolates the server's
runtime data but not the import-time initialization. Fix direction: honor
`TOWNSQUARE_DB`/a `--db`-equivalent at import (env var is read at line 135, so
`TOWNSQUARE_DB=<throwaway> python3 -m pytest` already avoids it — document that
as the required invocation).

### P2-3. Malformed JSON yields misleading 403 on `/fb_react` (and `/vote`) JSON paths
`POST /fb_react` with `Content-Type: application/json` and body `{broken,` →
**403** `{"error":"bad form token — reload and try again"}` instead of a 400.
Cause: `json_body()` (`app.py:401`) returns `{}` for unparseable JSON, and `{}`
passes the `isinstance(data, dict)` guard, so the CSRF check fires on the empty
dict before any JSON validation. The client gets "bad form token" for what is
really a malformed body. Fix direction: 400 on unparseable JSON in `json_body`
(or check `request.get_json` failure explicitly). Found by the adversarial
tester, cause verified in code. Not in prior 48h reports.

### P2-4. No security headers on any response
No `X-Frame-Options`, `Content-Security-Policy`, `X-Content-Type-Options`, or
`Referrer-Policy` anywhere in `app.py` (no `after_request` hook). For a
session-authenticated app this leaves clickjacking/MIME-sniffing exposure.
Found by the adversarial tester, confirmed by code search. Not in prior 48h
reports.

### P2-5. Server-rendered `#handle-chip` is empty (no-JS cosmetic)
`templates/base.html:77` renders `<span class="hint" id="handle-chip"
title="Your posting handle"></span>` with no text; only client JS fills it
later. With JS disabled a logged-in user gets no handle indicator in the
header. Trivial cosmetic. Found by the human tester. Not in prior 48h reports.

## INCIDENT — real-tree writes during this run (read carefully)
Two boundary breaches occurred; both investigated, one fully remediated:

1. **`townsquare.db` (checkout's real local DB) was modified** — mtime bumps at
   02:47 and 04:53 UTC. Mechanism: P2-2 above — `init_db(DB_PATH)` at app import
   runs schema ensures/seeds against the default DB before `--db` rebinds.
   Triggered by (a) the full pytest suite importing `app`, and (b) every
   `app.py --db` boot. Impact check: **no QA/test rows leaked** — no QA handles
   in `users`, posts table holds the normal 7 rows. Writes were limited to
   idempotent schema ensures/seeds. The task's "never touch the real DB"
   boundary cannot be met with `--db` alone; future runs must export
   `TOWNSQUARE_DB=<throwaway>` before any Python process imports `app`.

2. **Test uploads overwrote real files in `data/uploads/`** — the scratch DB's
   `video_uploads` ids restarted at 1, colliding with real stored filenames:
   - `vid-1.mp4` was the real **episode-03-visual.mp4 (7,579,864 bytes)**,
     overwritten by a 4295-byte test fixture at 02:45. **RESTORED byte-identical**
     from `/home/hatch/workspace/ts-spaces/musefm/assets/episode-03-visual.mp4`
     (sha256 `5ef3cfbd…193d9a` both copies; size matches the DB row).
   - `vid-2.mp4` was `clip.mp4` (2012 bytes, video row 2: handle `tester`,
     title "Test Title", status **rejected**, created 2026-09-18 — a prior run's
     test junk, referenced by no post). Overwritten; **no recoverable copy
     found** anywhere on disk. No user impact (rejected test artifact).
   - 11 other scratch files (`vid-3..9.mp4`, `img-1/2.png`, `gif-1.gif`,
     `1.wav`) had no real-DB references and were deleted.
   The uploads dir now contains only pre-existing files plus the restored
   `vid-1.mp4`. Root cause is the same non-hermetic upload dir (known issue);
   the filename-collision overwrite is the sharp edge. Recommend namespacing
   scratch upload dirs per run (e.g. `DATA_DIR` env honored for uploads).
