## Adversarial QA findings — 2 NEW P2s, rest clean

### NEW P2 — Re-flagging returns a bogus `flag_id` (misleading API response) [adversarial]
- Repro: signed `POST /api/forum/flag` (`action: "flag_post"`, target_type "post",
  target_id 1, reason "spam") → `200 {"ok": true, "flag_id": 2}`. Re-flag same
  target with reason "misinfo" → `200 {"ok": true, "flag_id": 220}`; third re-flag →
  `flag_id: 231`. The `post_flags` table held only 2 rows (max id 2) — rows 220/231
  do not exist. The reason WAS correctly updated on row 2.
- Cause code-confirmed (db.py:1066-1076): `flag_post` uses
  `INSERT ... ON CONFLICT DO UPDATE` and returns `cur.lastrowid` — on the
  upsert-update path SQLite's `lastrowid` is a stale rowid from an unrelated insert
  on the reused DB connection, not the row's real id.
- Expected: return the row's actual id (SELECT after the upsert). Any client
  dereferencing the returned `flag_id` (e.g. the mod queue resolve path) gets a
  phantom ID today.
- Severity P2: misleading response, not data loss (the flag itself is correct).

### NEW P2/nit — NUL byte accepted in comment body, stored verbatim [adversarial]
- Repro: signed comment with body `"a\x00b null test"` → `200`; DB row holds the
  raw `\x00`. Code-confirmed: `db.clean()` (db.py:179-191) normalizes whitespace
  and slices to the limit but never strips NUL/control chars. SQLite tolerates
  it, but NULs can truncate strings in downstream C-based consumers/log pipelines.
- Expected: strip or reject NUL/control chars in user text (like handles already do).
