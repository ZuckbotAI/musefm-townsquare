## P1 — likely new

### 1. Unauthenticated junk burns the shared `wr_api` rate budget (workroom DoS-of-feature)
- Repro: `for i in $(seq 1 35); do curl -s -X POST -H "Content-Type: application/json" -d '{"junk":1}' http://127.0.0.1:8473/api/workroom/create; done`
  then a VALID signed request:
  `python3 advqa_sig.py workroom_create /api/workroom/create '{"name":"advqa room","visibility":"private"}'`
- Response: `429 {"error":"rate limit hit — slow down, friend","ok":false}`
- Expected: malformed/unauthenticated requests should 400/401 WITHOUT consuming
  the rate budget, matching the codebase's own documented fix pattern
  ("P2 2026-09-19" comments on /api/identity/register and /api/forum/post:
  "Validate BEFORE counting the rate budget").
- Cause: `api_workroom_create` (app.py ~7502) calls `check_limit("wr_api", 30)`
  BEFORE `json_body()` parsing and signature verification. Same ordering issue
  on `/api/upload/gif` (app.py ~5467: `check_limit("gif_upload", 10)` before
  `verify_signed_body`) and **`POST /api/asks`** (app.py ~6413:
  `check_limit("ask_post", 5)` before `_asks_asker` auth — code-confirmed, not
  live-demoed: burning the 5/hr budget would lock sibling testers out).
  The codebase's own documented rule (P2 2026-09-19 comments) says: validate
  shape/auth BEFORE counting the rate budget.
- Note: budget is per client_ip() per hour (REMOTE_ADDR only, XFF untrusted —
  good). From one IP, 30 junk POSTs lock out legitimate workroom creation for
  an hour. Self-DoS only per IP, but on shared egress/NAT one bad actor locks
  out everyone behind it.

## P2 — nits / inconsistencies

### 2. `GET /api/openmic/tonight` returned 200 with an auth-error body (observed once, not reproduced)

  Single route definition, no before_request hook explains it.
- Expected: error bodies should never ship with 200. Unexplained transient —
  flagging with exact evidence; could not reproduce.

### 3. `GET /api/identity/register` → 404 instead of 405
- Repro: `curl -s -o /dev/null -w "%{http_code}" http://127.0.0.1:8473/api/identity/register` → 404.

### 4. `POST /flag` unauthenticated returns 401 status with an HTML redirect body

  "Redirecting..." HTML page.
- Expected: JSON 401 like `/fb_react` (`{"error":"sign in to react",...}`).

### 5. `Server: Werkzeug/3.1.8 Python/3.12.3` header discloses stack versions
- Repro: `curl -s -D - -o /dev/null http://127.0.0.1:8473/api/health | grep -i ^server`
- Expected: suppress or genericize on anything internet-facing (fine for local dev).

### 6. Comment bodies silently truncated at 2000 chars (HTTP 200) instead of rejected
- Repro: signed `POST /api/forum/comment` with
  `{"post_id":9,"body":"<20000 x chars>"}` → `200 {"ok":true,"id":6,...}`.
  Stored body length verified via `GET /api/forum/post/9`: **2000 chars**.
- Expected: `400 "comment body too long"` — matching the convention the
  codebase itself established: post bodies reject overlong input
  (P1 2026-09-20 00:46: "body too long (max N characters)") and post titles
  reject instead of silently truncating (P2 2026-09-20 03:35: "overlong titles
  were silently truncated — reject with 400 instead"). Comments still take the
  old silent-truncation path (`db.clean()` returns `s[:limit]`, so
  `if not clean(body, 2000)` only catches empty bodies).
- Impact: silent data loss — a user pasting a long comment loses 90% of it
  with a success response.
