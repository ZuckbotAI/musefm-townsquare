### [P2, NEW] Login rate limit: 10/hr per IP → ~55-minute lockout
- **Repro:** `for i in $(seq 1 12); do curl -s -o /dev/null -w "%{http_code} " -X POST http://127.0.0.1:8473/login -d 'handle=QaProbe&password=supersecret1'; done` → first 10 pass, then `429` with `Retry-After: 3315` and body "rate limit hit — slow down, friend".
- **Expected:** brute-force protection, yes — but 10 attempts/hour/IP with a 55-minute lockout is harsh for legitimate users (a few typos = locked out for nearly an hour), and on shared IPs (CGNAT, offices, this very test box) one actor's typos lock out everyone. Code: `rate_limit_message("human_login", 10)` in `login()`, keyed by `client_ip()` (REMOTE_ADDR via ProxyFix — correct per-real-IP on Render, but shared-IP collateral remains).
- **Test-harness impact:** I tripped this bucket; **new logins on this box 429 until ~18:46 CDT**. Existing sessions are unaffected (verified: old session cookie → `GET /settings` 200). Sibling testers with live sessions are fine; any fresh login before 18:46 CDT will 429.

### [P2, NEW, low risk] Login does not clear/regenerate the session first
- **Repro (code read):** `login()` in app.py sets `session["fm_id"] = ident["fm_id"]` without `session.clear()` (logout does clear).
- **Expected:** best practice is to rotate/clear the session on privilege change (login).
- **Actual risk: low.** Flask uses client-side signed cookies; the cookie value changes on mutation and an attacker can't forge the post-login value without the secret key, so classic session fixation isn't exploitable here. Flagging for hygiene only.

### [P2, observation] `Server: Werkzeug/3.1.8 Python/3.12.3` header on all responses
- **Repro:** `curl -s -D - -o /dev/null http://127.0.0.1:8473/` — every response carries the exact framework version.
- **Expected:** minor; dev-server header. Worth confirming production (gunicorn/Render) doesn't echo a version string the same way. Fingerprinting aid, not a hole.
