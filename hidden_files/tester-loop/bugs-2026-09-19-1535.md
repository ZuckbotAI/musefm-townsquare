## New P2s this run (5)

1. **Nonce burned before the rate-limit check on `@require_agent_or_signature` routes**
   (agent tester). Repro: `POST /api/forum/post` with a valid signed body →
   `429 {"error":"rate limit hit — slow down, friend"}`; resend the *identical*
   body → `401 "musefm-v1 auth failed: replay: nonce already used"`. The
   decorator (`app.py:435`) calls `verify_signed_body` (which consumes the
   one-time nonce) before the route body calls `check_limit`, so every 429
   forces the client to re-sign. Non-decorator routes (e.g. `/api/identity/update`)
   run `check_limit` first — inconsistent ordering across route types.
   Verified in code: `verify_signed_body` precedes `fn(*a, **kw)` in the
   decorator, and `check_limit` lives inside the route bodies.
   Cross-ref: 03:35 dismissed "nonce burns on 429" as a per-scheme nit — this
   is the more actionable angle: the ordering is *inconsistent*, not just
   unfriendly.

2. **Rate-limited human form POSTs return raw JSON instead of the form page**
   (human tester). Repro: hit the `post` 5/hr budget, then form-encoded
   `POST /submit` (logged in) → HTTP 429 with body
   `{"ok":false,"error":"rate limit hit — slow down, friend"}` (application/json).
   A human in the real UI sees a JSON blob instead of the form re-rendered
   with a friendly error. Expected: render the template with an error message
   like other form errors do. Verified in code: `check_limit` (app.py:481-483)
   unconditionally returns `jsonify`, and `/submit` (app.py:1009-1011) returns
   `hit` directly. **Proven by failing test** in
   `test_testerloop_flag_messages_2026_09_19.py`
   ("429 on form /submit renders HTML, not JSON").

3. **`/flag` JSON error message misleads on invalid reason** (human tester).
   Repro: `POST /flag` JSON `{target_type:"post", target_id:<valid>, reason:"test flag"}`
   (logged in, valid CSRF) → 400 `{"error":"bad flag target"}`. The target was
   fine — the *reason* was invalid (must be spam/harassment/nsfw/misinfo/other).
   Verified in code: `db.flag_post` raises the accurate
   `ValueError("bad reason (spam, harassment, nsfw, misinfo, other)")`
   (db.py:992), but `flag_web()`'s except clause (app.py:3907) swallows it into
   the generic "bad flag target". Cross-ref: 09-18 filed the *form-path*
   silent-302 on `/flag` bad reason/target_type — this is the JSON-path twin
   (different code path, different symptom). **Proven by failing test** in
   `test_testerloop_flag_messages_2026_09_19.py`
   ("flag invalid-reason message mentions 'reason' (not 'target')").

4. **Validation-failed requests burn the rate-limit budget → hour-long legit lockout**
   (adversarial QA). Repro: 30 rapid malformed POSTs to `/api/identity/register`
   → first 6 got 400, rest 429. The 1-hour 10/hr bucket counts validation-failed
   requests too, so all *legitimate* registrations from the same IP were then
   locked out for a full hour (the probe had to seed identities through
   `db.register_identity` instead). Attackers can't hurt anyone but themselves —
   but in shared-IP deployments (or with parallel agents) one noisy tester
   burns the budget for everyone. Distinct from the 03:35 "per-process in-memory
   rate-limit buckets" design note (that's about buckets being per-process);
   this is about *counting-before-validation* ordering.

5. **`GET /episodes/` → 404 instead of 308 redirect to `/episodes`**
   (adversarial QA, trailing-slash polish nit).
