## NEW findings (not in bugs-2026-09-22/23 files — checked)

### P2-1 — Login-gated HTML pages answer 200 with the login page instead of 302/403
Repro: `GET /mod/flags`, `GET /settings`, `GET /workroom/invites`, `GET /mod/uploads`
(no cookies, no session).
Status: 200, body = "Log in — MuseFM" page (~15.4 KB), no redirect, no data leaked.
Expected: 302 → /login (or 403). A 200-OK login page on an admin/mod path is a
status-code lie; crawlers could index it and scanners read it as "accessible".
No data leaks — the gate itself works.

### P2-2 — No rate limiting observed on public GET endpoints
Repro: 40 sequential `GET /api/shorts?limit=5` in 2.2 s → all 40 returned 200.
20 rapid `POST /api/forum/react` (unauth) → all 401, none 429.
Expected: some throttle (even generous) on hot public reads. Signed endpoints DO
have per-action buckets (observed a 429 "rate limit hit — slow down, friend" on
the shared-IP `post` bucket, and `react` is declared 120/hr) — so the machinery
exists; public GETs just aren't in it.

### P2-3 — `/api/shorts/cards?page=-1` echoes `"page": -1` in the JSON response
Repro: `GET /api/shorts/cards?page=-1` → 200
`{"html":"","next_page":null,"ok":true,"page":-1,"seed":"...","total":0}`.
The underlying `videos.shuffled_short_page()` clamps page ≥ 0 internally, so the
query itself is safe — but the route echoes the raw client value back.
Expected: normalize before echo (`"page": 0`). Cosmetic.

### P2-4 (code note, behavior currently safe) — `/api/shorts` passes raw `limit` into query fns
The docstring says "?limit= (default 10, max 50)" but app.py passes the raw int
to `videos.shuffled_short_page()` / `videos.list_shorts()`; clamping to ≤50
happens inside those functions (videos.py:697, videos.py:638). Verified:
`?limit=999999` and `?before=<id>&limit=999999` both return ≤50 rows. Behavior is
safe today, but the "max 50" contract lives one layer away from the route — a
future caller that skips those helpers inherits the unbounded value.
