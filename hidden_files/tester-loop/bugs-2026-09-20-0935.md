## NEW P2 — Handle validators disagree (loose valid_handle vs strict IDENTITY_HANDLE_RE) [human, code-verified + failing test]

`db.py` ships two handle validators with different contracts:
- `valid_handle` (db.py:194): `[A-Za-z0-9_-]{2,32}` — dashes, min 2
- `IDENTITY_HANDLE_RE` (db.py:449): `[A-Za-z0-9_]{3,20}` — no dashes, min 3

Signup and identity registration use the strict one, so no
dash/2-char handle exists in the DB today — no live hole. But the
loose `valid_handle` guards LIVE paths: app.py:559 (agent-author
handle claim), app.py:6711 (`/agent/<handle>` page), app.py:6819
(endorse target), plus db.py:793/864/951/1009/1426/1507/2387
lookups. Any future write path using `valid_handle` would mint
handles the identity system refuses to recognize, and the error
messages already contradict each other
("bad handle (3-20 chars: letters, numbers, _)" vs
"bad handle (2-32 chars: letters, numbers, _ -)").

Expected: one validator, one contract.

Proof: new failing test file
`test_testerloop_handle_consistency_2026_09_20.py` (repo root,
uncommitted, tests-only): 24 passed / 3 failed — the 3 failures are
the exact mismatch cases (`"ab"`, `"has-dash"`, 21-char handle).

## NEW P2 nit — Rate-limited /submit can surface 403 "bad form token" instead of 429 [adversarial, live-observed; NOT reproduced in isolation]

Reporter's repro: hammer ~15 quick requests, then immediately
`POST /submit` with a then-current CSRF token → 403
"bad form token — reload and try again". Server log showed genuine
429s on POST /submit in the same window, so the limiter was active;
the 403 read as token-state churn from limiter × per-session token.

Verification attempt (this run, coordinator): could NOT reproduce.
Fresh-instance probe via Flask TestClient on a throwaway DB:
5 valid posts → 302s, 6th post → clean 429 with Retry-After (both
with fresh and reused token); 15 rapid parallel GETs then POST →
429. Live probe on the test instance: token unchanged across 15
parallel GETs (tokens are stable per session — `_csrf_token()`
only mints when missing, app.py:716). The reporter's run shared
127.0.0.1 rate buckets with two sibling testers hammering
simultaneously, so the "valid" token may have belonged to a churned
session — a harness artifact, not a verified rate-limiter/token
interaction bug.

Filed honestly as a nit: IF a stale token meets an exhausted bucket,
users see a misleading "reload and try again" (the CSRF check runs
before the rate-limit check, app.py:1256-1287). Impact: cosmetic
only; no data loss, no bypass. No failing test written — the clean
path demonstrably returns 429, and a test for the un-reproduced
scenario would be speculative.
