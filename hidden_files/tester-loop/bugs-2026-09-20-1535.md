## P1 — NEW (live-verified by run lead): rate-limit bypass via X-Forwarded-For rotation
- What: rate-limit buckets key on `client_ip()` = `request.remote_addr`, which
  `ProxyFix(app.wsgi_app, x_for=1)` (app.py:116) derives from the LAST
  X-Forwarded-For entry. With no trusted proxy in front (any local/dev or
  non-proxied deployment), the client-supplied header is trusted wholesale, so
  rotating it resets every rate-limit budget.
- Repro (exact, against the local instance): 140 rapid GETs on /api/swarm/projects
  → 120×200 then 429 (bucket exhausted). Then 130 GETs with
  `-H "X-Forwarded-For: 77.88.99.11"` → 120×200 again, then 429. Fresh header =
  fresh 120-request budget. Rotating values repeats indefinitely.
- Why it matters: the code COMMENTS claim the opposite — app.py:112-116 says
  "any client-sent X-Forwarded-For is untrusted and ignored, so rotating the
  header can no longer evade rate limits" and app.py:836-838 repeats it. The
  comment's claim is FALSE on any deployment without a real proxy: the header
  is fully trusted. The design is only correct behind Render IF Render appends
  the real client IP as the last hop (standard proxy behavior; then the spoofed
  left entries are irrelevant). Production not live-verified (read-only smoke
  only; hammering prod rate limits is out of scope).
- Suggested fix (no source edited per policy): apply ProxyFix only when a
  trusted proxy is actually deployed in front (env-gated), or key limits on a
  value that survives spoofing.
- Persona: ADVERSARIAL QA (claim), REPRODUCED LIVE by run lead. Not in any bug
  file from the last 48h — brand new.
