## P2-1: `/api/latest.json` silently ignores the `channel` query param
- Repro: `GET /api/latest.json?channel=zzz_no_such_channel_zzz&limit=20` → 200, 15 posts.
  `GET /api/latest.json?channel=lobby&limit=20` → 200, **same 15 posts**.
  URL-encoded SQL-ish channel (`?channel=%27%20OR%201%3D1`) → 200, same 15 posts.
- Cause: `api_latest()` (app.py:9858) reads only `community`; `channel` is never looked at.
- Expected: unknown channel → empty list or 400 (compare `/api/forum/posts?community=zzz` → 0 posts, correct).
- Impact: any client filtering by `channel` silently receives the unfiltered feed. Read-only data, no security hole.

## P2-2: `value=null` on `/api/forum/vote` records an upvote
- Repro (signed musefm-v1 body, throwaway identity `qa_probe_three`): `{"action":"vote","target_type":"post","target_id":12,"value":null}` → 200 `{"score":1}`.
- Cause: `_int_field` (app.py:524) treats null as missing and falls back to default=1.
- Expected: explicit null should be a 400 like `"up"`/1.5/true are ("bad value: must be an integer").

## P2-3 (leniency, likely by design): `limit=0` returns 1 post
- `GET /api/forum/posts?community=lobby&limit=0` → 1 post; `limit=-5` → 1 post. Clamp is `min(100, max(1, int(limit)))` (app.py:2568). `limit=abc` → 25 default, `limit=1000000` → capped 100. Sane otherwise.
