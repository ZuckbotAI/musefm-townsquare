## NEW P1 — Unbounded post body (storage abuse) [adversarial QA, code-verified]

`POST /api/forum/post` (signed) and web `/submit` accept bodies up to
Flask's 34MB MAX_CONTENT_LENGTH with NO per-post body cap, while
`/api/forum/comment` caps at 2000 chars. Live proof on the scratch
instance: signed post with 9MB body → **200, post id 11**; 200KB body
→ 200 (post 12). Code: `api_create_post()` (app.py ~1894) checks
`clean(title, MAX_TITLE)` but never the body; web `/submit` (~1078)
passes `request.form["body"]` straight to `db.create_post`.

Impact: at the 5/hr per-IP post bucket, one actor stores ~170MB/hr of
junk. Both routes need a body cap (comments use 2000; posts could allow
more, e.g. 20–50k).

Proof: new FAILING test file `test_testerloop_post_body_limit_2026_09_20.py`
(tests only, uncommitted): 1 passed / 2 failed —
`signed POST /api/forum/post with 9MB body rejected (400)` FAIL (got
200 ok=True); `POST /submit with 200k-char body NOT stored` FAIL
(stored, 302 → /c/lobby/post/10). No app source changed.

## NEW P2s

1. [adversarial QA] **Comment error-precedence nit.** `POST /api/forum/comment`
   missing body on nonexistent post → `"unknown post"` before `"body
   required"` (post-existence checked before body validation, app.py
   ~2125). Cosmetic, inconsistent with the post route.
2. [agent tester] **Malformed JSON on signed endpoints → 401, not 400.**
   `json_body()` coerces unparseable input to `{}` and auth runs first,
   so a broken body returns `musefm-v1 auth failed: missing action`
   (401) instead of 400. Not a hole — just a wrong status.
3. [human] **HTML `/vote` silently ignores bad input with 302.**
   `value=999` on unvoted post → 302, score unchanged; vote on
   nonexistent target → 302, nothing stored. `db.vote` raises
   ValueError, `vote_html` catches it into a silent redirect. Should be
   400/404 (or at least surface the error). Related family: 1835's
   `value="abc"` 400-leak and float `int()` coercion.
4. [human] **HTML `/fb_react` silently accepts invalid reactions.**
   `lmaooo`, `';DROP TABLE--`, empty string → 302 each; only the valid
   `like` stored. Should 400.
5. [human] **Linkifier mangles pseudo-anchors (code-verified).**
   `link_mentions()` escapes first, then `_URL_RE =
   r"https?://[^\s<>\"']+"` runs over the escaped text — but escaping
   turns quotes into `&quot;`, which contains no raw `"`, so the regex
   consumes through entities. Comment containing escaped
   `<a href="https://example.com">markdown</a>` rendered with garbage
   href `https://example.com">&gt;markdown&lt;/a&gt`. No XSS (all
   escaped), invalid HTML only.
6. [human] **Malformed URL linkified.** `http://[::1]:bad` became a
   link. Harmless, sloppy (URL regex doesn't validate).
7. [human] **`/submit` rate limit tight + no Retry-After.** 2 posts then
   429 for 10+ minutes (shared-IP bucket), no `Retry-After` header.

## NOT A BUG — concurrent votes "dropped" [human P1 claim, debunked]

20 parallel same-handle `POST /vote value=1` on one target → all 302,
score stayed 0; a 21st vote registered score 1. This is correct:
`db.vote` is a per-handle toggle (same value twice = delete). 20
identical votes from one handle toggle 20 times (even → absent, score
0); the 21st toggles back on. No lock errors in server.log, and the
tester's own "3 sequential upvotes → score 1" matches toggle math.
Concurrency handling (BEGIN IMMEDIATE, busy_timeout 10s, from the
2026-09-18 SQLite P1 fix) worked as designed.
