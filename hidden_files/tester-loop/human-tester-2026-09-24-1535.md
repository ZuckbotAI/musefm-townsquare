## Bugs

### P1 — Forum search 500s on long `q` (CONFIRMED; already reported by adversarial tester this run — new detail: the web UI is affected too)

- SEV: P1 (broken feature — unauthenticated client can 500 a public read endpoint)
- REPRO: `GET /api/forum/posts?q=` + 60000 `_` chars → HTTP 500
  `{"error":"internal error — try again, and flag it if it repeats","ok":false}`.
  Also `GET /c/lobby?q=` + 60000 `_` chars → HTTP 500 (HTML).
  Adversarial tester's report (adversarial-2026-09-24-1535.md) covers the API
  endpoint with 60k "A" chars; I confirm it and add that the HTML community page
  (`/c/lobby`, app.py:1261) 500s identically. Sibling endpoints are fine:
  `/api/shorts?q=<60k>` → 200, `/api/episodes?q=<60k>` → 200.
- EXPECTED: 200 with results, or a clean 400 "query too long".
- ACTUAL: 500. Root cause: `db.list_posts` (db.py:991) interpolates raw user input
  into `LIKE '%{search}%'` with no wildcard escaping and no length cap; SQLite
  raises `OperationalError: LIKE or GLOB pattern too complex`. Pre-existing
  tracebacks for the same endpoint in server.log at 20:48:43, 20:51:03, 21:02:18,
  21:02:54 UTC. No existing test covers it.

### P2 — Bad `gif_url` burns post rate-limit budget before being rejected

- SEV: P2
- REPRO: POST /submit with valid title/body/community but
  `gif_url=https://evil.com/x.gif` → passed text validation, consumed one of the
  5/hr "post" budget, then → 429 on subsequent attempts (the 400 for the bad URL
  never surfaced because the budget was exhausted first).
- EXPECTED: input validation (gif whitelist) should reject before the rate budget
  is touched, like the text-field validation does (per the 2026-09-20 comment in
  app.py:1430, validation was deliberately moved before the bucket for 400s).
- ACTUAL: `_gif_from_form` runs inside the try block AFTER `rate_limit_message`,
  so a mistyped gif URL costs a post attempt. (`gifs.valid_gif_url` itself is
  strict — https-only, host whitelist, .gif path — the bug is only the ordering.)
