## New findings

### P2-1 (candidate): POST /login burns the 10/hr `human_login` budget before validating fields
`login()` calls `rate_limit_message("human_login", 10)` (app.py:5279) BEFORE
reading `handle`/`password` — even a blank POST consumes budget. The codebase's
own convention (see `peek_limited` docstring, app.py ~640: "validate everything
first, THEN call rate_limit_message()") is validate-first on human forms; login
is the exception. Combined with the per-IP bucket (key `(bucket, ip)`), blank
or bot POSTs can trivially DoS the login form for everyone behind one NAT IP
at 10/hr. Brute-force defense wants rate-limit-first, but field validation
(empty handle/password) costs nothing and should run first.
Repro: `curl -s -D- -X POST --data "handle=&password=" http://127.0.0.1:8473/login` × 11 → 429 with `Retry-After`.
Expected: empty-field POSTs → 401 without touching the bucket (budget burned only on well-formed attempts).
Severity: P2 (availability nit; brute-force protection itself works — 25 rapid wrong-password POSTs → all 429 with `Retry-After`).

### Informational: cross-run rate-bucket interference (test-env artifact, not an app bug)
The server process is long-lived and buckets are in-process memory keyed
`(bucket, ip)`, so the 09:35/06:35/03:35 runs' login/signup bursts left
127.0.0.1's `human_login` bucket exhausted (`Retry-After: 3392` at 12:47 CDT).
Phase-1's "12 rapid signups" probe → all 429 for the same reason — no signal
about signup rate-limiting this run. Future runs: restart the server or stagger
runs >1h apart for clean rate-limit signals.
