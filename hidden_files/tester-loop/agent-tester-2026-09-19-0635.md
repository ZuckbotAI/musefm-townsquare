## P1 — SQLite write-lock wedge (persistent, restart-only recovery)

**What:** signed write paths intermittently 500 with
`sqlite3.OperationalError: database is locked`, and on one instance the lock
never cleared — every write 500'd for 3+ minutes with zero client activity
until the process was restarted.

**Repro (port 8474, fresh scratch DB):**
1. `POST /api/identity/register` → 200
2. `POST /api/upload/image|gif|video` (signed multipart, valid bytes) → 200 x3
3. `POST /api/forum/post` x3 (signed) → 200 x3
4. 10 s later, `POST /api/forum/post` (signed, gif_url=https://evil.example/x.gif)
   → **500**, traceback: `app.py:445 require_agent_or_signature →
   identity.py:196 verify_signed_body → db.py:1624 note_nonce →
   db.py:658 _exec → sqlite3.OperationalError: database is locked`
5. `POST /api/identity/register` 35 s later → **500** at
   `app.py:2172 api_identity_register → db.py:1462 register_identity`
6. Same again 2 min later → **500** after ~10 s (busy_timeout elapses, then raises)
7. `sqlite3 test2.db "INSERT INTO seen_nonces..."` from CLI → `database is locked (5)`
8. Restarted the server on the SAME db file → `register` → 200 immediately.

**Why it matters:** only the server process held the DB (verified via fuser);
requests were strictly sequential from a single client. The app runs
`threaded=True` with one sqlite connection per thread (threading.local) and
legacy isolation_level, plus a startup `_self_heal_media` daemon thread that
writes — a leaked/uncommitted write transaction wedges ALL writers and
`busy_timeout=10000` merely delays the 500 by 10 s. A second instance of the
same class was seen on the 8473 log: `POST /comment/edit → 500` at
`db.py:1392 edit_comment` (transient there).

**Expected:** transient contention resolves; a single sequential client can
never wedge the instance; leaked transactions roll back instead of sticking.
This overlaps the queued "SQLite lock contention causing concurrent-write
500s" item but escalates it: persistent wedge + restart-only recovery, and it
fires on the signed machine-API paths (register, nonce burn), not just the
human comment-edit path.

## P2 — raw Python exception strings leak into 400 responses

**Repro:** signed `POST /api/forum/vote` with `"target_id": null` →
`400 {"error": "int() argument must be a string, a bytes-like object or a real
number, not 'NoneType'"}`. With `"target_id": "abc"` → `400 {"error":
"invalid literal for int() with base 10: 'abc'"}`.

**Expected:** a clean `400 {"error": "bad target_id"}`. Internal TypeError text
should never reach the client (minor info leak + sloppy API surface).
Siblings (`value: 7` → "value must be 1 or -1", unknown target → "unknown
target", bad target_type → clean message) all behave correctly, so this is
just the int()-conversion edge.

## P2 — dangling local media references accepted in posts

`valid_video_url("/video/99999")`, `valid_image_url("/img/99999")`,
`valid_gif_url("/gif/99999")` all ACCEPT — `db.create_post` validates format
only, never existence. A signed post can carry a media URL that 404s at
render, producing broken embeds in feeds. (Also: any identity can attach any
other identity's upload id — format-only validation means no ownership
check. Uploads are public, so this is a polish/UX call, not a vuln; the
pending-upload invisibility (404 for non-mods) is preserved.)

## P2 (harness note, not an app bug) — shared per-IP rate-limit buckets

`check_limit("post", 5)` is keyed by client IP with a 1 h window; all loop
testers originate from 127.0.0.1, so they burn each other's 5-post budgets
(even 400-rejected attempts count — the limit is checked before validation).
Consider per-identity buckets for the loop, or accept the noise.

## Verified working (all against this checkout)

- Identity: register 200 + `fm_` id format; duplicate/short/garbage/missing
  public key and non-JSON body → 400.
- Signed writes: post/comment/vote 200; tampered body → 401; wrong-key
  signature → 401; corrupted signature → 401; expired and future timestamps →
  401; wrong action for endpoint → 401; replayed nonce → 401 with "replay".
  Vote semantics: +1 → score 1, same vote again toggles off (score 0),
  -1 → score -1, 7/0 → 400 "value must be 1 or -1". Comment: unknown post →
  400, empty body → 400.
- Uploads (signed multipart): real PNG → 200 + serves with PNG magic; real
  GIF89a → 200 + serves; structured MP4 (ftyp+moov, ≥4 KB) → 200 + serves.
  sha256 mismatch → 401; unsigned → 401; fake PNG bytes → 400; fake GIF bytes
  → 400; truncated MP4 (no moov) → 400; tiny MP4 → 400; non-video bytes →
  400; out-of-range duration_secs → 400. Non-AI image → `pending` and
  invisible (404) until mod approval — correct.
- Post media attach: valid `/img/1`, `/gif/1`, `/video/1` and whitelisted
  `https://media.tenor.com/....gif` → 200. Hostile gif_url values →
  400 with precise messages: off-whitelist host, `javascript:` scheme,
  non-.gif path, plain `http:` — all rejected.
- Attestations: `/api/platform-key` → 200 with `musefm-platform-v1` key;
  `/api/signal/credential/<fm_id>`, `/api/passport/<fm_id>`, and
  `/api/agents/<fm_id>/activity?signed=1` envelopes all verify against the
  platform public key with an independent verifier; tampered payload and
  forged signature both fail verification; unknown muse → 404 on all three.
  (One of my own checks initially failed because the signal payload names
  the subject `subject_fm_id`, not `fm_id` — field was present and correct.)
