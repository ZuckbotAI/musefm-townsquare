## Findings

### RE-CONFIRMED (known) — intermittent 500 `database is locked` on write paths [P1]

**Repro:** any signed write (`POST /api/forum/post`, `/api/forum/vote`,
`POST /api/identity/update`, `POST /api/rewards/heartbeat`,
`GET /api/identity/<fm_id>`) intermittently returns
`500 Internal Server Error` with this traceback tail (9× on my instance, 1× in
:8473's `server.log`):

```
File "app.py", line 445, in wrapper
    ident = verify_signed_body(data, db, expected_action=action)
File "identity.py", line 196, in verify_signed_body
    if not db.note_nonce(nonce, NONCE_TTL_SEC):
File "db.py", line 1624, in note_nonce
    self._exec("DELETE FROM seen_nonces WHERE expires_at <= ?", (now(),))
File "db.py", line 658, in _exec
    cur = self.db.execute(sql, args)
sqlite3.OperationalError: database is locked
```

Each failed request hung ~10 s first (the `PRAGMA busy_timeout = 10000`), then
raised. Failures came in bursts correlating with heavy parallel load on the box
(sibling human/adversarial testers hammering :8473). Reads never failed; the
first write in the pipeline (`note_nonce`'s DELETE) is where it surfaces.
Mechanism: SQLite single-writer lock + slow fsync under contention; the existing
mitigations (WAL, per-thread connections, 10 s busy_timeout) narrow the window
but any commit slower than 10 s still 500s. Already in the defect queue
("SQLite lock contention causing concurrent-write 500s") — this run adds fresh
evidence and exact tracebacks, not a new bug.

### P2 (new) — image upload has no structural validation

```
POST /api/upload/image  (signed, file_sha256 correct, ai_generated=true)
  file = 320 bytes starting with real PNG magic + garbage
→ 200 {"ok":true,"id":2,"image_url":"/img/2","status":"approved"}
```

`ai_images.create_image_upload` checks magic bytes (PNG/JPEG/WebP) and size only;
`videos.create_video_upload` additionally requires the container's media index
(`validate_video_structure`). A corrupt-but-magic-valid image is stored as
`approved` and embeds as a broken image. Cosmetic only — no XSS/smuggling vector
(the bytes really start with image magic; browsers just fail to decode).

### Observations (not bugs)

- **Nonce burns on 429:** a validly-signed request that is later rate-limited
  (429 from `check_limit`, which runs after the auth decorator) still burns its
  nonce — the replay check is last in `verify_signed_body` but the whole
  verifier runs before business logic. Correct per the documented scheme
  ("only a validly-signed request can burn a nonce"); clients must re-sign with
  a fresh nonce after a 429. Verified live: 1st attempt `429`, identical retry
  `401 replay: nonce already used`.
- **Shared rate-limit buckets:** `client_ip()` uses REMOTE_ADDR only (XFF
  untrusted by design), so all local testers share the per-IP buckets. My :8473
  probes hit `429` on `/api/forum/post` (5/hr/IP) because sibling testers had
  consumed the bucket. Rate limiting itself is working as designed.
- `POST /api/forum/comment` with `post_id: null` → `400` with a slightly leaky
  message (`int() argument must be a string…not 'NoneType'`). Harmless; P2 nit.
