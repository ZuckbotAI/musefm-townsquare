## NEW P1 (coordinator-verified live + in code; failing test proves it)

### **P1 — `GET /api/forum/posts?q=<60000 chars>` → HTTP 500 (uncaught `sqlite3.OperationalError: LIKE or GLOB pattern too complex`)**
- [adversarial QA; coordinator re-verified live: 1000 chars → 200, 60000 → 500; traceback in `hidden_files/tester-loop/server.log`]
- Repro: unauthenticated `GET /api/forum/posts?q=` + 60k `A` chars → **500**. [human tester adds the web-UI twin: `GET /c/lobby?q=` + 60k chars → **500** too — same `list_posts` path.]
- Expected: 200 with results, or a clean 400 "query too long".
- Root cause: the `q` string flows into a LIKE pattern with no length cap — `app.py:2571 api_posts` → `db.py:991 list_posts` → `db.py:817 _q` (`self.db.execute(sql, args).fetchall()`), raising `sqlite3.OperationalError: LIKE or GLOB pattern too complex`. `_q` catches `OverflowError` (int64) but not `OperationalError`. Sibling endpoints (`/api/shorts?q=<60k>`, `/api/episodes?q=<60k>` → 200) don't share the flaw.
- Any unauthenticated client can 500 a public read endpoint with one request. Server recovers cleanly (`/api/health` 200 after); no data loss — P1, not P0.
- Proving test: `test_testerloop_search_q_500_2026_09_24.py` — `test_long_search_q_does_not_500` FAILS as designed (raises the OperationalError); control passes.

1. **P2 — Missing `signature` field reports "bad signature encoding" instead of "missing signature".** [agent tester; coordinator-verified live: deleted `signature` from an otherwise-valid signed body → `401 {"error":"musefm-v1 auth failed: bad signature encoding"}`; verified in code too]
   Repro: `POST /api/forum/post` with a valid musefm-v1 signed body (action/fm_id/timestamp/nonce/community/title/body present and correctly signed) minus the `signature` key.
   Expected: 401 `musefm-v1 auth failed: missing signature` — matching the established pattern: missing timestamp → "missing timestamp" (P2 fix 2026-09-21), missing nonce → "missing nonce" (P2 fix 2026-09-24 06:35).
   Root cause: `verify_signed_body` (identity.py:156) passes `data.get("signature")` straight into `b64u_decode`; `None` raises `IdentityError("not a base64url string")`, re-raised as "bad signature encoding" (identity.py:199-201). A garbage signature ("!!!notb64!!!") returns the identical message, so clients can't distinguish absent from malformed. Needs the same `if signature is None: raise IdentityError("missing signature")` guard the timestamp/nonce paths got.
   Proving test: `test_testerloop_sig_missing_2026_09_24.py` — fails as designed; 2 controls (garbage sig → "bad signature encoding", valid body → 200) pass.
