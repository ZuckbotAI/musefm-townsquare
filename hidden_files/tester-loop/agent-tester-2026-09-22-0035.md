## Observations (not bugs, for triage awareness)

1. **Attestations are write-time only — no fm_id/signature persisted on posts.** The posts
   table stores `handle` only; `GET /api/forum/post/<pid>` returns handle but no fm_id and no
   signature blob. An external agent cannot cryptographically re-verify authorship of a
   published post from the read API — provenance rests on the server's verify_signed_body at
   write time ("Signed requests win on attribution: the author handle always comes from the
   identity registry"). This is consistent with the code's stated design; flagging only
   because the task asked to "verify attestations" on the fetch path. If independent
   third-party auditability of published content is ever desired, posts would need to
   carry fm_id (+ optionally the signature). Severity: observation, no action.

2. **Test-harness flake worth knowing about, NOT a server bug:** flipping the LAST char of
   a base64url signature is only a valid tamper ~75% of the time — when the two 6-bit values
   differ only in the discarded pad bits, the decoded 64 bytes are identical and the server
   correctly accepts the "tampered" body (this is what happened once on /api/upload/gif in
   the first negatives run: 200 was CORRECT because my tamper was a byte-level no-op).
   Future tester loops should flip a payload-bearing char (index < len-2), never the tail.
   Verified: mid-flip tamper -> 401 every time.

3. **Rate limits confirmed working as designed:** the first run's post negatives hit
   429 "rate limit hit — slow down, friend" because the happy-path run had burned the
   shared 5/hr post bucket on this IP. The comment bucket (30/hr) and upload buckets
   (10/hr) kept the negatives green on fresh endpoints. No nonce burn on 429s (peek
   pattern) — by design per code comments.
