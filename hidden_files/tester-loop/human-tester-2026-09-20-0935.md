## Findings
**P2 — Handle validation inconsistency:** `db.py:valid_handle` allows `[A-Za-z0-9_-]{2,32}` (dashes, 2–32 chars) while `IDENTITY_HANDLE_RE` (used by /signup) requires `[A-Za-z0-9_]{3,20}`. Signup uses the strict one, so no live hole — but the two validators disagree and `valid_handle` is the looser one. Worth unifying.

## Could not fully test live (methodology note, not an app bug)
Rate-limit buckets are keyed by client IP, and all tester subagents share 127.0.0.1 — the 5/hr post and 30/hr comment buckets were exhausted by sibling testers, so live submission of the XSS post, emoji-flood post, 10k-char body post, and weird `gif_url` values was blocked with 429s. Mitigations used: (a) XSS verified against the verbatim `link_mentions`/`_valid_url`/`_URL_RE` code — safe; (b) code confirms `len(body) > MAX_BODY (10000)` → 400 and title > 200 → 400 before the rate bucket is touched (validate-first, good); (c) `gifs.valid_gif_url` requires https + whitelisted host + `.gif` path. **Recommendation for future runs:** give each tester persona its own source IP (or a rate-limit bypass header) so write-bucket tests don't interfere.
