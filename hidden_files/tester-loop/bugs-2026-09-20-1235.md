## P1 — NEW: SESSION_COOKIE_SECURE on plain HTTP breaks human session login on local/test instance
- What: POST /login with valid creds → 302 + Set-Cookie, but the cookie carries the
  `Secure` flag. Browsers never send a Secure cookie over http://, so every follow-up
  request has an empty session → 302 back to /login. Human session login is 100% broken
  on the plain-HTTP local/test server (and any local dev server run without --debug).
- Repro (exact, against the local instance): fresh boot; register `qaprobe3` via /signup;
  POST /login → 302, `Set-Cookie: session=…; HttpOnly; Path=/; SameSite=Lax; Secure`;
  any subsequent browser-over-http request → 302 to /login?next=… . Note: curl -b
  manually-passed cookies DID work in earlier tester runs, masking this.
- Root cause (verified): app.py:355 `app.config["SESSION_COOKIE_SECURE"] = not app.debug`.
  The local server runs debug=False → Secure on, even over plain HTTP. The code comment's
  stated intent ("Off under app.debug so local plain-HTTP development servers can still
  log in") is not achieved, because the local server isn't run with --debug.
- Verified live this run: `curl -s -D - http://127.0.0.1:8473/` returns
  `Set-Cookie: session=<redacted>; HttpOnly; Path=/; SameSite=Lax; Secure` over plain HTTP.
- Impact: LOCAL ONLY — production is HTTPS, unaffected. But it silently broke the
  human-tester lane's authenticated coverage this run (all authenticated adversarial
  probes were blocked by it; earlier runs' "passing" session tests used curl-cookie hacks).
- Suggested fix (no source edited per policy): gate SESSION_COOKIE_SECURE on a real
  HTTPS indicator (env flag / request scheme) rather than `not app.debug`.
- Persona: ADVERSARIAL QA (recovered report). Not in any bug file from the last 48h.
