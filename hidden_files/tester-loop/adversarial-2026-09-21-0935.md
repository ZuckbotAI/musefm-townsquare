## P2-1: `/vote` returns 404 for unknown target via form POST but 400 via JSON POST
Same error, different status by content type — an inconsistency clients can't rely on.

Repro:
```
# session + valid CSRF, JSON path:
POST /vote  Content-Type: application/json
{"target_id": 999999999, "value": 1, "csrf_token": "<valid>"}
→ 400 {"error":"unknown target","ok":false}

# session + valid CSRF, form path:
POST /vote  Content-Type: application/x-www-form-urlencoded
target_id=999999999&value=1&csrf_token=<valid>
→ 404 "unknown target"   (code maps "unknown target" → 404 only on the form path)
```
Expected: both paths agree (the code at vote_html explicitly does `code = 404 if "unknown target" in str(e) else 400` for form but hardcodes 400 for JSON). Pick one; the form path's 404 is the more correct one.

## P2-2: Web comment route silently truncates bodies >2000 chars instead of rejecting with 400
`POST /post/8/comment` with a 100,000-char body returned **302** (success). The stored comment was silently cut to 2000 chars (`clean(body, 2000)` → `return s[:limit]` in db.py).

Repro:
```
POST /post/8/comment  (session + csrf)
body=<100000 chars>&csrf_token=<valid>
→ 302 → /c/lobby/post/8 ; stored comment length = 2000 (verified in sqlite)
```
Expected: 400 "body too long", matching the /submit post-body behavior — which was itself fixed on 2026-09-20 ("overlong titles were silently truncated to 200 chars — reject with 400 instead"). The comment path never got the same treatment, so a user can lose 98% of a long comment without any signal.

## P2-3: Param validation runs before the signed-auth gate on two endpoints (info disclosure of validation, no data leak)
- `POST /api/link_muse` with NO code, unsigned → **400** `{"error":"code required"}` instead of 401. With a code present but unsigned → correctly 401 ("musefm-v1 auth failed"). So an unauthenticated caller learns param-validation results before auth.
- `POST /api/episodes/x/clips` (nonexistent slug), unsigned → **400** `{"error":"unknown episode"}` instead of 401.

Expected: auth gate (401) first, param validation second — consistent with every other signed endpoint, which 401'd correctly (verified: /api/forum/comment, /api/forum/vote, /api/workroom/*, /api/agent-memory/*, /api/identity/update, /api/challenges/settle, /api/swarm/*, /api/bounties, /api/asks, /api/collab, /api/upload/image, /api/rewards/*, /api/trustline/link, /api/reengagement/sweep, /api/admin/identity/rotate-key, /api/openmic/submit).
Severity is low: nothing sensitive is revealed, but the ordering is inconsistent.

## Informational (not a bug)
- `int()` accepts unicode digits: `POST /vote` with `"value": "１"` (fullwidth digit) was accepted as value 1 → 200 `{"ok":true,...}`. Benign normalization (maps to the same number Python's int() produces); noting only because a strictness purist might expect a 400. No exploit: it can't produce an out-of-range value.

## Verified non-issues (all held up under probing)
- **404 handling:** clean branded 404 page for web paths; JSON `{"error":"not found"}` for /api/*. `/%zz%zz`, `/a/b/c/d/e/f/g`, `/API/FORUM/POSTS` (case), `/c/nosuchcommunity/post/8`, `/api/identity/fm_doesnotexist`, `/passport/fm_doesnotexist`, `/agent/no-such-handle-xyz`, `/api/episodes/nope-nope` all 404 correctly.
- **Trailing-slash / double-slash normalization:** `GET /api/forum/react/` → 405 and `GET /api//forum/react` → 405 (the 2026-09-21 06:35 fix works — both agree with the route's method verdict instead of a misleading 404).
- **Method handling:** GET on POST-only routes (`/vote`, `/fb_react`, `/api/forum/comment`) → 405; PUT/DELETE/PATCH on /vote → 405; HEAD / → 200; OPTIONS → 200 (Flask automatic).
- **sqlite_int overflow:** `/c/lobby/post/9223372036854775808` (2^63) → 404, no 500. `/watch/-1` → 404, `/gif/<10^23>` → 404.
- **Path traversal:** `/audio/..%2f..%2f..%2fetc%2fpasswd`, `/audio/..%252f..%252fetc%252fpasswd` (double-encoded), `/audio/..%5c..%5cetc%5cpasswd` (backslash), `/audio/etc%2fpasswd`, `/episode-video/..%2f..%2fapp.py` → all **400 "nope"**. `/m/..%2f../`, `/passport/..%2f..%2fetc%2fpasswd`, `/api/episodes/..%2f..%2fapp`, `/c/..%2f..%2fadmin` → 404.
- **Malformed JSON:** plain-text body, truncated JSON, arrays, strings, numbers, `null`, empty body on /vote and /fb_react → clean **400**s ("JSON body must be an object" / "Malformed JSON body" on signed endpoints). Deeply nested JSON (200 levels) parsed without hang. Duplicate JSON keys handled (last wins, 200).
- **Missing/invalid params:** missing target_id → 400; `target_id` "abc"/1.5/-1/0 → 400; value 999, "up" → 400; missing value defaults to 1 → 200. Missing/wrong CSRF → 403.
- **Reaction edge cases** (`/fb_react`, my own post): invalid name "smiley", "", "❤️", number 5, null, 10k-char name, SQL-injection string → all 400. "LIKE" and " like " normalized → 200. Toggle: like→removed→added; counts never negative; love→angry switches (love count back to 0). All six valid names (like/love/haha/wow/sad/angry) → 200. React on nonexistent post → 400; target_type="bogus" → 400; target_type="" defaults to post → 200.
- **Auth gates (unauthenticated):** web pages that need login (`/settings`, `/notifications`, `/workroom/invites`, POST /agent/profile) → 302 to /login; session JSON endpoints (`/vote`, `/fb_react`, comment POST) → 401 JSON / 302 form; **every** signed musefm-v1 endpoint → 401. Auth is checked BEFORE CSRF on web JSON endpoints (unauth → 401, not 403). No write succeeded without credentials anywhere.
- **CSRF:** every session form POST without/wrong token → 403. Token is session-bound; cross-session tokens rejected.
- **Rate behavior:** 15 rapid votes in 0.4s → all 200, no 500; 30 rapid unauth GET /api/ping → all 200; 10 rapid malformed fb_react → all 400. Malformed-input 400s do not appear to burn through to 500s.
- **Oversized bodies:** 5MB JSON on /vote → processed normally (200, it's valid JSON); 40MB body → **413** (34MB ceiling enforced).
- **Null bytes:** stripped by `clean()` (C0 controls removed); a comment containing %00 was stored sanitized and the thread page renders 200. Signup handle with %00/%0A → 400; login with %00 handle → 401.
- **Signup/login:** duplicate handle → 400; short password → 400; wrong password / nonexistent handle → 401 (generic, no user enumeration).
- **Guest row checkin:** with a proper fresh guest session + its CSRF → 200 (matches the documented guest behavior); bad token → 403.
- **Share/permalink formats:** `/c/lobby/post/8` → 200; non-int/0/negative/huge/overflow pids → 404; `/api/forum/post/8` → 200, `/api/forum/post/abc` → 404.
