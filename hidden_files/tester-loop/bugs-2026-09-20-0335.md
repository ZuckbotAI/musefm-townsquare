## NEW P2 — Invalid HTML form POSTs burn the rate-limit budget [human, live-proven + failing test]

The 2026-09-19 validate-before-limit fix covered the signed API paths
(validation runs before `check_limit` records the hit), but the human
HTML form routes still call `rate_limit_message()` FIRST — and
`limited()` (app.py:569) appends the hit to the bucket before any
validation runs, so 400-rejected requests consume budget.

Live repro (scratch instance): 1 valid signup + 4 invalid (password
mismatch → 400, no account created) exhausted the 5/hr `human_signup`
bucket; the next VALID signup → 429. Same pattern in `submit()`
(app.py:1212, rate check before body-length/title validation) and
`add_comment` (app.py:1337, rate check before `db.create_comment`
validation).

Impact: a typo costs the budget; on a shared IP (or by an attacker
firing garbage requests), legitimate users get locked out of signup /
posting for an hour.

Proof: failing test file `test_bugfix_form_ratelimit_burn_2026_09_20.py`
(tests only, repo root, uncommitted) — 2 passed / 2 failed:
`valid signup after 5 invalid ones is NOT rate-limited — got 429`,
`valid post after 5 overlong ones is NOT rate-limited — got 429`.

Note: 2026-09-19-0635.md observed "400s burn budget too" but dismissed
it as a loop-harness artifact. This run proves it's real app behavior.

## NEW P2 — Overlong titles silently truncated to 200 chars [human, code-verified]

`submit()` (app.py:1231) raises an explicit "body too long" for bodies
> MAX_BODY, but titles go through `db.create_post` →
`clean(title, MAX_TITLE, single_line=True)` (db.py:795/179), which does
`s[:limit]` — the tail is silently dropped with no notice. Expected:
a 400 "title too long (max 200)" matching the body behavior.

## NEW P2 nit — JSON vs form status inconsistency on unknown reaction target [human, code-verified]

`vote_html` (app.py:1363) and `fb_react_web` (app.py:4118): JSON path
returns 400 `"unknown target"`; form path maps it to 404 (per the
2026-09-20 00:46 P2 comment — "surface the error"). The 404-on-form was
a deliberate fix, so this may be by-design; flagging as nit in case a
single status per error is preferred.

  comment/vote → media upload (GIF/MP4/PNG, sha256-attested) →

  (unsigned/wrong-key/replayed nonce/stale timestamp/unknown fm_id).

  (action="workroom_create") → 200.
