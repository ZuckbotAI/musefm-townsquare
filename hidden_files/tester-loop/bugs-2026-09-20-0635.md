## NEW P1 — POST /vote with missing/empty `value` silently records +1 [human, live-verified + failing test]

`_int_field(data, "value", 1)` (app.py:1462) falls back to default 1
(upvote) when `value` is missing or empty. Consequences:

- A valueless form POST returns 302 and **records an upvote** instead of
  erroring (verified via Flask TestClient on a throwaway DB:
  explicit -1 → stored -1; missing value → flipped to +1).
- It can silently UNDO a deliberate vote: an existing -1 downvote is
  flipped to +1 with no indication (and an existing +1 is toggled off
  by the db.vote() same-direction toggle, so a malformed request
  destroys a legitimate vote).
- JSON path returns 200 `{"ok": true, ...}` in the same situation.

Expected: 400 "value required" on missing/empty (form and JSON) —
matching the 2026-09-20 00:46 tester-loop policy already applied to
unknown vote targets in the same route ("bad input should surface
errors, not act silently").

Impact bounds: needs a logged-in session + valid CSRF token, so
exploitability is low; this is a semantics bug, not an auth hole.
But silent vote-flipping is data corruption of the most user-visible
kind.

Proof: failing test file `test_testerloop_vote_value_required_2026_09_20.py`
(tests only, repo root, uncommitted — per fix policy): 4 passed /
6 failed. All six failures are the missing/empty-value cases (302/200
instead of 400, vote flipped).
