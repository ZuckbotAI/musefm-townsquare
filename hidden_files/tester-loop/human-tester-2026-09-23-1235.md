## Bug list

### P2 — Overlong comments are silently truncated instead of rejected
- **Repro:** `POST /post/16/comment` (form, valid session + CSRF) with `body = "q"*2001`
  → HTTP 302 (looks like success).
- **Expected:** 400 "comment too long", matching post bodies (`/submit` rejects >10000 chars)
  and post titles (`/submit` rejects >200 chars) — the codebase already established
  "reject, don't truncate" as the rule (P2 2026-09-20 fixed silent title truncation).
- **What happened:** comment stored with `length(body) = 2000` (verified in sqlite:
  `SELECT id, post_id, length(body) FROM comments` → row `6|16|2000`). The user loses
  content with no warning.
- **Root cause:** `db.create_comment` does `body = clean(body, 2000)` and `clean()` ends with
  `return s[:limit]` (silent truncation); the route only checks `if not clean(body, 2000)`
  (truthiness), so anything ≥1 char passes. The signed-API comment path shares
  `create_comment`, so it truncates there too.
- **Suggested fix:** reject with 400 when `len(body) > 2000` before the rate budget burns,
  mirroring the `/submit` body check. (Fix policy says no source edits — filing only.)

### P2 (nit) — JSON vote/react on a missing target returns 400, form path returns 404
- **Repro:** `POST /vote` with `{"target_type":"post","target_id":999999,"value":1}` (JSON) → 400
  `{"error":"unknown target"}`; same request as a form POST → 404.
  `POST /signals/react` JSON on missing post → 400 likewise.
- **Expected:** consistent status (404) for "unknown target" on both paths.
- **What happened:** the JSON branches hardcode 400 (`if want_json: return jsonify(...), 400`);
  only the form branch maps `"unknown target"` → 404. Deliberate-looking, minor API inconsistency.

## Verified intended behavior (NOT bugs — do not "fix")
- **Repeat identical votes toggle off.** `db.vote` has an explicit `# toggle off` branch:
  voting +1 twice removes the vote (score 1 → 0); 10 rapid identical votes alternate
  0, -1, 0, -1… YouTube-style toggle, UI gets `my_vote` in the JSON response. Working as designed.
- **Reactions toggle/switch.** Same reaction twice → `action: "removed"`; different one →
  `"switched"`. Documented in the route docstring.
- **XSS: everything escaped.** `<script>` in title/body/comment/photo-title,
  `<img src=x onerror=…>`, `<svg onload=…>`, `[x](javascript:…)` hrefs, `data:` URLs —
  all rendered HTML-escaped (`&lt;script&gt;`, `&#x27;`, …). No raw `<img>`/`<svg>` tags in
  output; no `href="javascript:` anywhere. Bodies render as plain escaped text (markdown
  `[x](y)` link syntax is NOT linkified — `<strong>` worked in one spot, `#` headings did not
  become `<h1>`), so URL-scheme payloads cannot execute. Verified on thread pages
  `/c/lobby/post/16` and `/photos`.
- **Upload validation solid.** `/photos/upload`: valid PNG → 302; text-renamed-to-.png → 400
  "not a recognized image"; SVG-with-script → 400; 26 MB file → 400 "file too big (max 25 MB)";
  empty file → 400; wrong field name → 400; no file → 400; anonymous → 302 to /login.
  `/submit` attach: valid PNG → post created with `/img/<uid>` embed; fake PNG → 400;
  `gif_url=javascript:alert(1)` → 400. Pending uploads return 404 for non-mods/non-uploader
  (`_may_preview_pending`); only same-origin `/img/<uid>` URLs are embeddable
  (`valid_image_url` rejects external URLs — no hotlink/tracking-pixel vector).
- **Auth gates correct.** Anonymous `POST /submit`, `/post/<pid>/comment`, `/photos/upload`
  → 302 to `/login`; anonymous JSON `POST /vote`, `/signals/react` → 401 with `signin_url`.
  Wrong/missing CSRF on every state-changing human route → 403 (vote, react, submit, comment).
- **Validation-before-budget respected.** 10001-char body, 201-char title, blank title,
  unknown community → 400 without consuming the 5/hr post budget (subsequent real posts
  still succeeded until the shared budget ran out — see environment notes).
- **Rate limits fire.** 6th post within the hour → 429 with `Retry-After`; 11th login →
  429. `limited()` does **not** record a hit when the bucket is already full, so 429-storms
  don't self-extend the lockout (checked in code).
- **Login hardening.** Bad password → 401 generic "bad handle or password" (no handle
  enumeration); `?next=http://evil.example/x` and `?next=//evil.example/x` → `Location: /`
  (open-redirect closed); signup rejects `<script>`/too-short/too-long/space/SQL-quote
  handles, duplicate handles, and short passwords (all 400).
- **Vote/comment validation messages are clear.** `value=999`/`0` → 400 "value must be 1 or -1";
  `value=1.5` → 400 "bad value: must be an integer"; bad `target_type` → 400 naming the
  allowed types; unknown comment parent → 400; comment on missing post → 404;
  whitespace-only comment → 400; NUL bytes stripped by `clean()` (documented).

## Environment notes (for the loop coordinator, not app bugs)
1. **The :8473 server died mid-run.** At ~17:44:5x UTC the port went connection-refused;
   it was rebooted at 17:45:51 UTC (by the parent/sibling harness) with the correct
   `--db hidden_files/tester-loop/test.db`. The log shows no Python traceback — the original
   boot lacked the `SERVER_EXIT` wrapper, so crash-vs-kill is undetermined. Worth watching
   whether the instance survives a full loop.
2. **Rate-limit buckets are per-process memory but the IP is shared.** Sibling subagents
   hammering the same instance from 127.0.0.1 consumed the shared budgets: my 5th valid
   post 429'd (4 of mine + at least 1 sibling post in the hour) and the 10/hr `human_login`
   bucket filled (16 non-429 POST /login in the log across testers). Concurrent testers on
   one loopback IP will keep tripping each other's budgets — consider staggering, or
   per-tester ports/DBs.
3. **Test-client fallback used for the auth-blocked portion.** With login 429-locked,
   comment/vote/reaction tests ran via Flask `test_client` in-process with
   `TOWNSQUARE_DB=hidden_files/tester-loop/test.db` (same scratch DB, same app code,
   fresh in-process rate buckets). Results are equivalent at the Flask layer; HTTP
   transport itself was covered by the ~70 requests-phase checks.
4. **`SESSION_COOKIE_SECURE=True` over plain HTTP:** Python `requests`' cookiejar silently
   drops Secure cookies set over http (browsers accept them on 127.0.0.1 as a trustworthy
   origin). Not an app bug, but HTTP-level harnesses must manage the cookie manually —
   my first run's "not logged in" failures were this harness artifact, since corrected.
5. **Unexplained log entries:** 17× `POST /vote → 404` at 17:44:02–03 UTC in
   `hidden_files/tester-loop/server.log`, before my runs (probably a sibling's fuzzing —
   `/vote` exists and returns 401/403/200 normally). Flagging, not claiming as a bug.
